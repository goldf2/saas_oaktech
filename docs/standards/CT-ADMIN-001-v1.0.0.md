# 容器化业务系统：超管初始化与权限管理标准

- 标准编号：CT-ADMIN-001
- 规范版本：1.0.0
- 采纳日期：2026-09-16（Asia/Shanghai）
- 状态：已确认，作为需要用户与后台权限的容器化业务系统默认设计规范。
- 适用范围：本工作区自研或可改造的业务应用；部署平台可为 Coolify、Docker Compose 或其他容器编排平台。
- 实施边界：采纳规范不等于现有应用已实现。新增变量、页面、数据表和恢复命令，必须完成项目实现与验证后才能使用。本规范不是 Docker/Coolify 自动提供的功能，也不是完整容器运维规范的替代品。

## 1. 核心决策

**部署平台只提供首次初始化凭据；首次超管绑定完成后，人员角色由系统后台和持久化权限数据管理。**

标准流程：

```text
部署应用并接通身份登录与持久存储
  → 运维配置短时、一次性初始化口令
  → 部署负责人通过正常登录流程进入初始化页
  → 输入口令并确认将当前账号绑定为超管
  → 服务端原子完成身份绑定、超管授权和初始化关闭
  → 超管进入“用户与权限管理”授权其他管理员
  → 删除部署平台中的初始化口令配置
```

不用逐个把用户标识抄进环境变量；不把“第一个注册的人”自动设为超管；不配置长期通用的 `admin/admin` 账号；不通过关闭权限检查解决初始化问题。

新项目默认采用本标准。既有项目通过独立、可回滚的迁移接入，不因本规范被采纳就批量修改生产账号。静态网站、无用户后台的服务和第三方不可改造镜像不强制增加人类超管流程；例外在各项目决策记录中说明。

## 2. 身份与权限分别管理

认证回答“这个账号是谁”，应用授权回答“这个账号可以做什么”。默认复用已有身份系统，不为初始化超管另建一套永久用户名和密码登录。

已有 Casdoor/OIDC 的应用继续使用其正常登录流程。账号在本应用中以经过验证的 `issuer + subject` 绑定，不能以昵称、可修改用户名、邮箱或前端上传的身份字段直接授予权限。OIDC 对稳定身份的约定见参考 [1]。

初始化时由服务端从当前有效会话取得身份。页面可以显示当前账号供用户确认，但不得要求普通部署人员手工查询或复制 `subject`。若尚无身份提供方，必须先实现安全的本地账号注册/登录，再复用同一套账号体系绑定超管。

**应用超管不等于 Casdoor 全局管理员、Coolify 管理员、宿主机 root 或其他应用的超管。** 本规范统一流程，不强制各产品共享账号库或权限。多租户应用必须明确应用级与租户级边界，不允许租户管理员修改应用级超管。

## 3. 默认角色与最小权限

| 角色 | 默认权限 | 禁止事项 |
| --- | --- | --- |
| 超级管理员 `super_admin` | 管理本应用管理员、业务管理功能和授权审计；经确认转交超管职责 | 不自动获得身份平台或宿主机管理权限 |
| 管理员 `admin` | 执行被授予的业务管理操作，例如商品维护、软件发布 | 不能任命管理员、修改超管或给自己提权 |
| 普通用户 `user` | 使用已授权的个人与公共业务功能 | 不能访问管理数据或提交管理写操作 |

机器任务使用独立服务身份和最小操作范围，不复用人类超管的 Cookie、密码或初始化口令。例如“上传软件草稿”不自动包含“公开发布版本”或“管理管理员”的权限。

项目可以细分管理员业务权限，但必须保持权限默认拒绝、服务端逐请求校验与显式授权原则，见参考 [2]。

## 4. 初始化凭据的统一约定

应用实现下列两种凭据输入方式之一或两者；支持情况必须写入项目部署文档。通用变量名使用 `APP_` 前缀，具体应用可以换为自身前缀：

| 变量 | 含义 | 生命周期 |
| --- | --- | --- |
| `APP_BOOTSTRAP_ADMIN_TOKEN` | 运维通过运行时秘密变量注入的随机初始化口令 | 首次初始化期间 |
| `APP_BOOTSTRAP_ADMIN_TOKEN_FILE` | 应用读取的只读秘密文件路径，例如 `/run/secrets/bootstrap_admin_token` | 首次初始化期间；与直接口令方式互斥 |

商城采用前缀映射时，名称为 `OAKTECH_BOOTSTRAP_ADMIN_TOKEN` / `OAKTECH_BOOTSTRAP_ADMIN_TOKEN_FILE`。这些名称是实现契约，不是“现在填写后就会生效”的声明。

口令要求：由密码学安全随机源生成，至少 32 个随机字节；每个应用与环境独立生成，不使用人工短密码。v1.0 默认有效期为 60 分钟，从首次登记口令指纹时起计，并写入持久存储；容器重启不得延长同一个口令的有效期。这是本项目规范选择的参数，不是声称第三方标准规定了同一时长。

服务端持久化仅保留口令摘要/指纹、到期时间、消费状态和安装标识，不保存口令明文。高熵口令采用安全的摘要比对；用户密码仍遵循独立的密码存储规则，不能混用两种用途。已过期口令只能由有部署权限的人员更换，不能靠普通网页请求刷新有效期。

Coolify：只在目标业务应用的运行时秘密变量中配置，不启用构建期注入。Docker Compose：可用按服务授权的秘密文件；`_FILE` 是应用需要实现的读取约定，不能假设 Compose 会自动转换自定义变量。平台行为见参考 [3]、[4]。

口令不得进入 Dockerfile、镜像层、Git、前端 `NEXT_PUBLIC_*` / `VITE_*` 配置、URL 查询串、日志、监控事件或截图。初始化页不加载第三方统计脚本。删除秘密配置并重建容器不会撤销已经写入数据库的超管角色。

## 5. 首次初始化必须原子完成

初始化页面建议使用 `/setup/admin`，角色管理页面建议使用 `/admin/users`；框架可以采用等价路由，但导航文案与行为应一致。

初始化提交必须同时满足：受信任的正常登录会话、用户确认绑定当前账号、有效初始化口令、未完成的初始化状态，以及 CSRF/来源校验。公开环境使用 HTTPS，初始化接口限制尝试频率；GET 只显示状态，不授予角色。相关请求保护见参考 [5]。

在一个数据库事务中完成以下操作：检查并锁定本应用的初始化状态；校验口令未过期且未消费；取得已验证的当前身份；写入超管角色；消费口令；写入永久完成标记与审计事件。事务任一步失败，均不留下“有超管但未关闭初始化”或“口令已用但没有超管”的半状态。

多个容器或多个并发请求只能有一个成功首次绑定。单进程内存队列、浏览器按钮禁用、先查后写而无锁，均不能作为初始化互斥保证。

持久状态至少区分：

| 状态 | 允许行为 |
| --- | --- |
| 从未初始化且无有效口令 | 不开放超管认领；提示部署配置缺失 |
| 从未初始化且有有效口令 | 正常登录后可提交一次超管绑定 |
| 已初始化 | 拒绝所有再次认领，即使环境中仍残留旧口令或换了新口令 |
| 存储不可读、状态损坏、已初始化但超管不可用 | 拒绝特权操作，进入运维恢复流程；不得当成新安装 |

不能仅根据“管理员人数为 0”判断能否重新初始化。初始化标记独立于用户记录，删除、禁用用户或更改环境变量都不能自动重新打开首次认领。

## 6. 日常管理员管理

首次通过正常登录建立本应用最小用户记录后，超管可在后台选择账号、查看当前角色、授予或撤销管理员、转交超管职责。默认只管理本应用已建立关联的身份，不拉取整个身份平台的私人资料。

所有授权变更在服务器执行；目标用户标识与角色均校验。普通管理员只能做业务操作，不能调用角色管理接口。新增、禁用、删除、降级和超管转交必须写入审计记录。

角色变更不要求修改环境变量或重启应用。撤销提交后发起的下一次受保护请求必须按新角色校验；不能把长期 JWT 内的旧角色或浏览器缓存当作唯一授权来源。关键写操作在其事务提交前再次确认所需权限；对已执行的操作不宣称能追溯撤销。

服务端可直接查权限库，或使用具备跨实例失效与版本检查的缓存。权限存储故障时，特权操作拒绝执行，不退回旧环境白名单或默认放行。

不能删除、禁用或降级最后一名在本应用中有效的超管。两个并发角色变更也不能共同移除最后一名超管；需通过事务与锁保证。该约束不能防止身份平台在应用外删除账号，因此仍必须有独立恢复流程。

新增/转交超管属于敏感操作，需要确认与近期重新认证；生产超管应启用身份提供方的多因素认证。更多审批或强制双人复核可按项目风险另行规定。

## 7. 持久化、部署与备份

用户身份映射、角色、初始化状态和审计事件保存在事务性持久存储中，不写容器临时目录，不与公开下载目录混放。单实例可采用挂载持久卷的事务数据库；多副本必须共享能提供相应事务/锁语义的存储，不能各有一份独立权限文件。

重启、升级镜像、滚动部署不会丢失角色或重新初始化。数据库/持久卷缺失或不可写时，管理功能不就绪；不能退回空内存数据库并开放认领。部署清单必须明确数据卷、数据库权限、秘密注入和备份位置。

备份必须覆盖角色、身份映射和初始化完成标记；恢复演练要验证三者一致。恢复旧快照可能重新带回后来已撤销的权限，所以恢复后必须重新对账管理员名单、处理旧会话和轮换相关秘密，不能仅验证页面能打开。

登录所需身份服务不可用时，不得因此授予管理权限。已设计为匿名公开的静态文件或软件下载继续保持独立服务边界；不应为了检查管理员而让公开下载强依赖登录系统。

## 8. 从环境白名单迁移

对已有 `OAKTECH_ADMIN_SUBJECTS` 等白名单的应用，采用一次性、可核验的迁移，而不是同时长期保留两套最高优先级授权来源。

迁移前备份，盘点实际受信任身份并由部署负责人明确首位超管；不能把所有历史普通管理员自动升级为超管。使用受控迁移或已登录且持有初始化凭据的绑定流程，将确认后的权限写入新的角色库与迁移记录。

新系统启用后，数据库成为人员角色的唯一日常授权来源。旧白名单停止参与授权，删除相关环境配置；不能在后台撤销后，又因旧环境变量仍存在而继续放行。

迁移、启用新授权路径、停用旧路径及回滚必须在项目运行手册记录。回滚旧代码若会重新启用白名单，应先审查已撤销权限，不允许把镜像回滚当作安全的授权回滚。

## 9. 超管丢失与紧急恢复

区分两类故障：忘记密码、MFA 丢失等身份问题优先走原身份提供方恢复；应用超管角色丢失或身份迁移走应用的受控运维恢复。

恢复流程由拥有部署/宿主机管理权限的负责人主动发起，先备份，再使用应用提供的受限 CLI 或维护任务，绑定经过核验的目标身份，并保留独立审计。恢复完成后撤销临时恢复授权、核对角色名单与会话。

不能复用已消费的首次初始化口令，不能清空初始化标记、删除数据库或设置 `DISABLE_AUTH=true` 来“恢复”。没有常驻免认证后门，没有公开网页一键重置超管。具体恢复命令必须随实现交付；本规范不虚构已经可执行的命令。

若提供短时网页恢复认领，必须由运维显式启用、使用独立的一次性凭据和受限入口，并且不能弱化正常认证/MFA。一次性凭据的随机、限时、单次消费等设计参考 [6]，这里用于应用恢复，不声称是第三方规定的容器启动协议。

## 10. 最小页面与交付物

| 交付物 | 验收内容 |
| --- | --- |
| 初始化页 | 显示当前登录账号和系统状态；口令不回显；成功后永久关闭首次认领 |
| 用户与权限页 | 只有超管能授予/撤销管理员；身份与角色清楚；不要求抄 subject |
| 权限不足页 | 区分未登录与无权限；给出正确入口，不泄露管理数据 |
| 授权审计 | 记录操作者、目标、角色前后值、时间、结果、请求标识；不记录秘密 |
| 部署样例 | 明确运行时变量或秘密文件、数据卷、首次初始化和删除口令步骤 |
| 迁移与恢复手册 | 明确旧白名单停用、并发约束、备份、恢复和回滚风险 |
| 验证报告 | 分开记录单元测试、隔离身份测试与真实部署/真实账号验收 |

## 11. 发布验收门槛

1. 新安装：没有口令、错误口令、过期口令、未登录、外部身份伪造、跨站请求均不能认领；正常登录加有效口令只能绑定当前账号。
2. 并发与故障：并发初始化只有一人成功；中途失败无半状态；同口令重启不延长有效期；成功后保留或更换环境口令也不能再认领。
3. 授权：普通用户与管理员不能修改角色；超管可以授权；撤销后的后续管理请求立即拒绝；并发操作不能移除最后超管。
4. 生命周期：重建容器、升级、删除初始化秘密后角色保留；持久存储故障默认拒绝；恢复备份后核对角色并处置旧会话。
5. 迁移：原有业务数据不丢失；旧白名单不再覆盖后台撤销；镜像回滚不会不经确认恢复已撤销角色。
6. 隔离：没有硬编码超管密码、无秘密进入镜像/前端/日志；机器身份不能管理人类角色；公开下载不因身份初始化或故障失效。
7. 操作闭环：从容器部署、身份登录、首次绑定、添加管理员到撤销管理员走完一次真实流程。模拟会话通过不能代替生产账号验收；未实现的环节必须明确列出。

只有上述相关验收完成，具体应用才能记录为“已按 CT-ADMIN-001 实施”。发布此标准文档本身不改变任何应用权限。
