# ADR-0001 · 管理员事务存储与现有JSON目录的一致性

日期：2026-09-16。状态：**ADM-01工程验证完成；选定后续实现路线，尚未接入生产授权。**

基线：`f8b0e8c796aac44309728f70fac1cd853437fe24` / `0.1.26`。本次原型位于 `scripts/admin-poc/`，不是正式 `lib/admin/`，不得从业务路由导入。实际验证见 [证据](../00-handoff/evidence/2026-09-16-admin-storage-poc.json)。

## 1. 决策

1. 权限持久化采用**PostgreSQL事务库**，角色、首次初始化消费、永久完成标记与授权审计同事务提交。初期使用单例installation行锁，以确定的顺序串行化很少发生的授权/最终管理提交，避免先做无必要的细粒度锁。
2. **不采用“SQL里查权限/拿锁，然后直接写现有catalog.json”作为一致性方案。** 真实故障试验证明，即使SQL事务最终失败，断开数据库连接的旧Node进程仍能在撤权已经返回后rename一个JSON文件，文件系统不会自动跟随SQL回滚。
3. 后续ADM-02/ADM-09采用**同一事务中的管理提交记录＋目录元数据快照＋审计**作为管理写入的提交点。原型以JSONB保存现有目录形状，证明不必立即拆解全部商品/版本关系就能实现事务一致性；正式schema和迁移仍需ADM-02/ADM-10交付。
4. 软件字节继续在现有持久文件存储，不塞进权限数据库；字节准备、哈希/签名校验在锁外，最终授权及版本引用在事务内。未关联到已提交公开版本的文件不能被下载。
5. **公开文件服务不查询用户角色库。** 后续由专用的、按revision有序的投影器把已提交的公开目录生成只读快照，匿名读取和已发布字节服务继续使用该快照。数据库不可用时不接受新的管理写入，也不让公开下载开始依赖登录或角色查询。投影器与其崩溃/顺序/落盘恢复尚未实现，必须在ADM-09/11验证后才能切换生产。

这里的“提交”明确指管理命令在PostgreSQL成功commit，而不是未来缓存投影更新时间。撤权返回后，不得接受新的旧权限管理命令；撤权之前已提交的合法变更不会被追溯撤销。若投影暂未落盘，界面必须显示“已提交、分发中”或等价明确状态，不能谎报已公开可下载；最终是否公开仍通过真实URL验证。

## 3. 实际代码与试验

- `scripts/admin-poc/schema.sql`：installation、principal、catalog、audit、committed_command五个试验对象。正式限流、凭据轮换、状态迁移与恢复表尚未交付。
- `store.mjs`：同连接事务、锁后初始化、角色变更、最后超管保护、目录版本与幂等命令。只接受试验身份，不承担HTTP身份认证。
- `worker.mjs`：独立Node进程/PG连接；支持测试屏障，允许父测试精确在锁内杀进程或终止其数据库会话。
- `run.mjs`：随机私有集群、SCRAM口令、loopback监听、fsync启用、真实关停重启与清理；也可连接显式指定的隔离CI测试库。
- 连接严格限定127.0.0.1和 `oaktech_admin_poc`；schema只接受本次随机前缀。永不读生产 `DATABASE_URL` / `.env.local`。

本机PostgreSQL报告17.10，分发包为 `@embedded-postgres/darwin-arm64@17.10.0-beta.17`。**二进制file检测为x86_64/arm64通用格式，但PostgreSQL启动信息报告x86_64构建；本轮未独立确认实际进程使用的架构，不能据包名宣称原生ARM服务器已验收。** CI另用Linux `postgres:17.10-alpine`，具体结果随运行收据独立记录。`pg@8.23.0` 仅加入开发依赖，现有生产页面和授权源不变。

## 4. 已复现的两个关键问题

### 4.1 PG-14：数据库锁不能保护外部文件原子性

可重现顺序：管理员A查权并持有installation锁 → 暂停A → 测试终止A的PG backend（锁释放） → 超管B撤销A并成功提交 → 恢复A，A仍能rename本地JSON → SQL commit失败，但JSON已改变。

这是刻意失败的设计对照。用例通过表示**证明该设计不安全**。测试只写自建临时目录，绝不接触实际catalog。简单增加“提交前再查权限”、捕获PG异常或设置更长锁超时，都不能提供跨资源原子性。

替代路线由PG-09/12/13证明：在同一个SQL事务内提交权限复核、canonical目录、不可变命令和审计；连接断开后，旧事务没有成功commit的路径。投影只能读取已提交命令，不得接收浏览器的任意JSON或带过期角色的旧请求。

### 4.2 PG-17：有效期必须在获得锁以后重新计算

最初原型用同一条 `SELECT ..., expires_at > clock_timestamp() ... FOR UPDATE` 得到有效期。在另一个进程持有行锁、口令等待期间过期的真实用例中，原型仍错误认领成功。原因是计算表达式的求值可发生在锁等待前，不能把它当成锁后的新时间检查。

修复为：先锁installation并验证安装标识，再另发SQL语句使用 `clock_timestamp()` 复核到期时间。新增PG-17在修复前实际失败、修复后通过。不可使用事务起点的 `now()`/`CURRENT_TIMESTAMP`代替实时到期判断。

## 5. 后续必须实现，不得把PoC当成完成

- ADM-02：正式schema/约束/迁移版本、安装ID核对、显式新安装准备、权限最小化；生产启动不自动创建空库并开放认领。
- ADM-03～08：正常OIDC会话、近期认证/MFA、60分钟凭据登记与轮换、CSRF、限流、初始化及管理页面。原型没有这些接口，不能直接暴露。
- ADM-09：同库canonical元数据切换、只读公开投影的白名单字段、递增revision、乱序拒绝、单写者锁/崩溃恢复、幂等重放、撤回和旧缓存边界；若无法证明投影一致性则阻止上线。禁止恢复未经授权的双写方案。
- ADM-10：已有商品/Release原样迁移与比对；旧白名单受控退出；投影不是备份或新的写入源。先暂停管理写入再切换权威源。
- ADM-11～14：私有网络和真实数据库部署、容器卷与备份恢复、真实身份预生产验收、负责人首次绑定。**此时才可以称超管已配置好。**

原有匿名下载使用已经发布的只读目录；本次没有改变这一实现。PG不可用期间维持已有公开内容与禁止新的管理提交是目标，不意味着“新发布内容也能脱离持久库随意更新”。撤回已缓存文件仍有既有不可变缓存边界。
