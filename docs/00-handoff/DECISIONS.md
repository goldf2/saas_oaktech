## DEC-20260906-02 · 按浏览器语言自动选择店面语言

- 状态：已确认
- 日期：2026-09-06
- 决策人：用户

### 决策

1. 首次访问根地址时读取浏览器发送的 `Accept-Language`，目前支持中文（`zh`/`zh-*`）和英文（`en`/`en-*`），无法识别时默认英文。
2. 语言优先级为显式 `/en` 或 `/zh` 路径 > 用户手动选择的 `oaktech-locale` Cookie > 浏览器语言 > 英文默认值。
3. 不使用 IP 地区推断；显式 URL 始终可用于分享、测试和覆盖自动选择。

## DEC-20260905-03 · OakTech 公共存储使用单一公开读 Bucket

- 状态：已确认，复用现有 Bucket
- 日期：2026-09-05
- 决策人：用户

### 决策

1. 使用现有 `oaktech-public` Bucket，作为橡树公司所有第一方应用的公共内容存储，不再新建同用途 Bucket。
2. Bucket 采用公共读、非公开写入；上传、更新和删除只能通过管理员或发布后台。
3. 公共内容以 `apps/<app-id>/` 前缀进行逻辑隔离，例如 `apps/gitfinder-desktop/brand/` 和 `apps/software-store/brand/` 。
4. 公共读不等于公开写入；用户配置、会话、Token、凭证、私有备份不得放入。
5. 全局名称冲突时使用带公司、区域或业务标识的稳定名称；不随意复用他人的通用 Bucket 名。
6. 当前列表中的 `oaktechz-public-read`、`oaktech-pub`、`oaktechpublic`、`oaktechzpublicread` 等相近名称暂作待清理项；清理前必须只读盘点对象、ACL 和最近访问，不得直接删除。
7. OSS 作为原始资源和唯一事实源；未来以 CDN 作为边缘缓存和分发层，CDN 不承担源文件管理、版本管理或回滚主责。
8. GitFinder Logo 等公开静态资源优先使用 OSS 作为源站、Cloudflare 作为缓存和稳定域名入口；不把生产容器文件系统当作唯一存储。若资源只随网站代码发布，也必须保存在 Git 仓库 `public/` 中并通过 Coolify 正常构建部署。
9. Casdoor 邮件验证采用“一个邮件 Provider 作为共享发信通道，按组织或应用配置不同邮件内容/品牌”的模型；只有发件地址、环境或限流隔离需要独立时才新增 Provider。

## DEC-20260904-02 · 软件商店采用 Apple 风格设计体系

- 状态：已确认
- 日期：2026-09-04
- 决策人：用户

### 决策

1. OakTech 软件商店的店面、登录页和发布后台统一采用 Apple 风格，但不复制 Apple 官网的品牌资产或页面结构。
2. 设计重点是清晰的信息层级、克制的系统色、平台系统字体、适量半透明材质、即时反馈和可中断动效，而不是单纯使用大面积毛玻璃效果。
3. Figma 作为视觉规范、组件状态和交互原型的事实来源；Next.js 组件仍是正式运行实现，不使用自动生成的 Figma 代码直接替代工程代码。
4. 优先建立颜色、字体、圆角、间距、阴影、动效和无障碍变量，再设计软件商店首页、软件详情页、登录页和发布后台。
5. 所有动效必须支持 `prefers-reduced-motion`，半透明界面必须提供高对比度或降低透明度的兼容表现。

### 体验目标

- 用户进入商店时感到安静、可信且容易理解。
- 下载、版本选择和发布状态是页面中的首要信息，不被装饰性效果抢夺注意力。
- 管理后台保持高信息密度，但通过分组、留白和渐进披露避免表单堆叠。

### 第一切片实现约束

- 用户侧页面使用 `--store-*` token 与 `StorefrontHome`、`ProductCard`、`StoreDownloadCard` 等轻量组件，不引入新的大型 UI 库。
- 首页从实际公开目录读取产品与当前版本，中文与英文复用相同结构；设计层不维护另一份发布事实。
- 当前版本页与历史版本页复用同一下载组件，下载 CTA 只消费现有 `publicPath`，不绕过制品校验或发布门禁。
- 半透明只用于导航和小型浮层；内容卡片保持稳定实色表面。系统要求降低透明度或提高对比度时切换为实色和明确边框。

## DEC-20260904-01 · Casdoor 作为 OakTech 统一认证技术栈

- 状态：已确认
- 日期：2026-09-04
- 决策人：用户

### 背景

OakTech 的软件商店当前使用 Supabase Auth，其他桌面工具和浏览器插件仍需分别建设登录。用户希望所有第一方工具获得统一、完整的注册、登录、找回、第三方身份源、会话和安全能力。

### 决策

1. 自托管 Casdoor 作为 OakTech 的统一身份提供方，计划使用 `auth.oaktechz.com`，应用统一通过标准 OIDC/OAuth 2.0 接入，避免绑定 Casdoor 专有 SDK。
2. 统一认证架构不强制统一账户。各产品可选择共享 Organization/账户域实现 SSO，也可使用隔离的 Organization/账户域；每个 Web、Electron、浏览器插件和机器任务必须创建独立 Application、Client ID、redirect URI、audience 和 scope。
3. Web 使用服务端 Authorization Code 流程，令牌由服务端管理，浏览器只持有 Secure、HttpOnly 会话 Cookie。
4. Electron、移动端和浏览器插件属于公开客户端，使用系统浏览器和 Authorization Code + PKCE，客户端内不得保存 Client Secret。
5. 软件发布等无人值守任务使用独立机器 Application 和 OAuth 2.0 Client Credentials，权限限制到所需 API；机器身份不能发布最终版本，仍保留后台人工确认。
6. 业务系统以 `issuer + subject` 作为外部身份键，不使用可变邮箱作为用户主键。
7. Casdoor 管理身份、登录方式、MFA、会话和基础访问控制；积分、订阅、订单、许可证、发布数据、配额和文件继续保存在各业务系统。
8. 软件商店管理员使用独立内部身份边界并强制 MFA，不直接把普通用户身份提升为全局后台管理员。
9. Casdoor、身份数据库、密码凭据、邮箱、手机号和完整身份档案部署并保存在阿里云中国内地节点；软件商店主站部署在境外，不建立境外身份数据库副本。
10. 境外商店通过服务端 Authorization Code 流程访问境内 Casdoor，只接收建立业务会话所需的最小 OIDC 声明；默认不把邮箱、手机号、头像和第三方账号资料写入 Token 或境外业务库。
11. 境外商店在本地缓存 OIDC discovery/JWKS 并验证已签发 Token，正常页面请求不逐次回连境内 Casdoor；首次登录、授权码交换、刷新和统一退出仍依赖境内认证服务。

### 迁移边界

- 不一次性删除 Supabase。第一阶段只替换身份与会话，Supabase PostgreSQL 继续承载现有积分、订阅和支付数据。
- 建立业务用户与 Casdoor `issuer + subject` 的映射，并保留旧 Supabase user ID 作为迁移字段，完成逐用户核对后再移除旧认证依赖。
- 迁移服务端 API 和数据库访问策略后，才能删除 `auth.users` 触发器、`auth.uid()` RLS 和 Supabase Auth SDK。
- GitFinder 保持本地优先：未登录、离线或 Casdoor 不可用时，本地核心功能不受影响；登录只启用云同步、授权和跨设备能力。
- “身份数据保存在境内”不等于登录过程中完全没有数据跨境：境外商店必须收到至少一个可识别用户的 `issuer + subject` 声明。该声明按最小化原则处理，并在隐私告知和个人信息保护影响评估中记录。

### 第一验收切片

1. Casdoor 生产实例和数据库可访问。
2. OakTech 可完成登录、回调、刷新、退出和管理员 MFA。
3. 现有 Supabase 用户能映射到同一业务用户，积分与订阅数据不丢失、不重复。
4. GitFinder 通过系统浏览器复用同一 Casdoor 会话登录，同时保持未登录可用。
5. 发布流水线能使用独立 Client Credentials 创建草稿，但不能绕过管理员发布门禁。
