计划版本：1.0.0；制定日期：2026-09-16；范围：`goldf2/saas_oaktech`。

**本文描述待实现方案，不是功能完成报告。** 实际任务状态只维护在 [TASKS.json](TASKS.json)，人类可读视图由 [PROGRESS.md](PROGRESS.md) 生成。当前事实见 [CURRENT_STATE.md](CURRENT_STATE.md)，执行入口见 [HANDOFF.md](HANDOFF.md)。

## 1. 目标、优先级与交付边界

用户确认的首要闭环：在 Coolify 配置一次性初始化凭据 → 用现有账号正常登录 → 系统自动绑定首位超管 → 超管在网站选择其他账号、授予和撤销管理员。不再要求用户反复查询或手工复制 `subject`。

权限功能必须遵守项目内固定快照 [CT-ADMIN-001 v1.0.0](../standards/CT-ADMIN-001-v1.0.0.md)。本轮文档任务只建立计划和追踪机制，不新增业务路由、不配置真实秘密、不变更生产账号。文档任务 PLAN-01 完成，不能计入 ADM 系列的功能完成率。

| 优先级 | 工作流 | 完成定义 |
| --- | --- | --- |
| P0 | 首位超管、角色管理、旧白名单退出 | 完成隔离测试和真实部署账号认领；后台授权/撤权可用 |
| P0 | 发布通道可追踪 | 分别核验代码、CI、实际部署、公开版本；定位当前部署凭据缺口 |
| P1 | Open Play 官网软件包正式发布 | 已授权管理员校验并发布真实包，官网清单/文件完整验证 |
| P1 | 软件发布稳定性 | 上传会话、目录写并发、审计失败恢复各有专项验收 |
| 后续 | GitFinder候选发布、OSS资源整理 | 重新确认候选与范围，不自动执行历史待办中的发布命令 |

不在本期内：重做商城视觉体系、引入第二套永久密码登录、迁移支付/积分/订阅库、默认全产品共享账户、自动公开历史草稿、跨项目批量授予权限、重写桌面应用。已有 Supabase/Creem 遗留功能保留，但不能把模板说明当作这些业务已验收。

## 3. 设计决策与未决问题

**已确认**：复用正常登录；应用级 super_admin/admin/user；随机一次性口令；永久初始化完成标记；角色持久化；后台撤权；旧白名单受控迁移；受控恢复。不是“给所有登录用户管理权限”。

**技术基线提案**：授权数据采用 PostgreSQL 独立 schema 和最小权限服务端连接；认证数据库仍留在现有身份服务中，不复制密码、手机号、完整档案。只保存商城身份映射与角色。优先验证这一条路线，不同时开发多个数据库适配层。

ADM-01 必须回答：目标数据库在哪里、是否允许使用已有实例的隔离 schema、连接/备份由谁配置、是否有跨实例事务连接、部署副本数和网络边界。以上没有被本轮实际配置。无法获取目标数据库时标记该环境工作阻塞，本地测试可用隔离实例；禁止回退为无持久性的内存角色或 `catalog.json` 角色表。

单机SQLite可作为经过ADR批准的替代方案，但不得声称多节点各自挂载独立SQLite就具备全局初始化互斥。项目商品目录仍是JSON，不因授权库采用PG就自动拥有多实例业务写事务。

安全默认参数提案：初始化口令至少32随机字节、持久有效期60分钟（标准已确认）；敏感超管操作要求最近5分钟内正常重新认证；初始化尝试按安装/身份/可信客户端地址共同限速，初始参考5次/15分钟并配全局上限。后两项是工程提案，需要在测试中验证，不能误称第三方标准强制阈值。

## 4. 持久数据模型与一致性

以下是设计结构，不是已部署数据库；最终SQL随 ADM-02 提交。

| 数据对象 | 核心字段/约束 | 关键要求 |
| --- | --- | --- |
| `admin_installation` | singleton key、installation_id、schema_version、phase、initialized_at、authorization_mode、revision | 单例预创建后加行锁；不能依据人数为0自动重开 |
| `app_principal` | UUID、provider、issuer、subject、role、status、authz_version、created_at、last_seen_at | unique(provider,issuer,subject)；role/status CHECK；不同issuer不得合并 |
| `bootstrap_token` | installation_id、fingerprint、registered_at、expires_at、consumed_at、revoked_at | 只存摘要；保留用过/过期指纹，轮换回旧值不重置寿命 |
| `admin_audit` | UUID、actor、target、action、before/after、outcome、request_id、created_at | 授权变更审计与角色同事务；不保存口令/会话/秘密 |
| `admin_request_dedupe` | actor、idempotency_key、operation、request_digest、result、created_at | 唯一约束；同key不同内容拒绝，避免重试重复授权 |
| `admin_attempt_limit` | scope_digest、window、count、blocked_until | 跨实例限速；不永久公开保存原始IP或Token |

v1只有应用级角色，不在此时做租户级、部门级、菜单级权限生成器。普通用户只在首次经服务端验证的登录/账号入口登记最小身份；默认角色user。避免在每次会话读取时无差别写库，从而拖慢公开页面。

用户选择界面不能依赖缺失的邮箱/姓名：当前会话已主动去除这些字段。使用系统生成短用户编号和可选的应用内备注/申请编号进行辨识；完整issuer/subject仅在需要的受保护诊断中显示。备注不是认证凭据，不能用于自动合并或授权。建议用户先正常登录并生成一次管理申请记录，超管从候选用户列表中选择；不拉全量Casdoor用户、不要求手工填写subject。

初始化单例、最后超管保护、角色变更都以统一锁顺序处理：installation行 → 按主键排序的principal行 → 业务记录/审计。并发死锁或序列化冲突仅允许有界重试，重试须保留幂等键。不能只依赖React按钮禁用或单进程Promise队列。[PG锁文档](https://www.postgresql.org/docs/17/explicit-locking.html)

## 5. 初始化状态机与秘密配置

计划支持运行时 `OAKTECH_BOOTSTRAP_ADMIN_TOKEN` 或 `OAKTECH_BOOTSTRAP_ADMIN_TOKEN_FILE`，二者互斥。拟新增 `OAKTECH_AUTHZ_DATABASE_URL`（服务端秘密）、`OAKTECH_INSTALLATION_ID`（每环境固定、非口令的安装标识）。这些变量目前不被业务程序处理；本轮不会把它们写入 `.env.example` 的现有可用配置区。

| 状态 | GET初始化页 | POST绑定 |
| --- | --- | --- |
| 未登记凭据/未授权准备新安装 | 告知运维准备步骤；不读出秘密 | 拒绝 |
| 凭据已登记且有效、尚未初始化 | 正常登录后显示当前身份与确认框 | 有效口令、来源/CSRF与限速均通过才允许 |
| 凭据过期或被撤销 | 提示运维更换口令 | 拒绝；重启/GET不得延长 |
| 已初始化 | 显示完成状态并进入管理页面 | 无论残留/更换口令均拒绝 |
| 存储不可读、安装标识不一致、完成标记异常 | 受限维护提示，不泄露内部连接 | 特权失败关闭，不当成新站 |

只有受控的安装准备/启动检查可以登记新口令指纹，不能让匿名GET创建installation或刷新过期时间。必须明确区分“经运维确认的新安装”和“原数据库丢失/连错空库”：固定安装标识、schema准备和持久安装登记进行对账；常规启动不能自动建空库并开放认领。ADM-02/ADM-11须用真实错库/缺卷故障验证此边界。

POST绑定事务顺序：验证服务端正常会话及近期认证 → 验证同源/CSRF/限速 → 锁installation → 验证安装、phase、摘要、有效期和未消费 → upsert当前principal → 授予super_admin → 消费口令 → 设置initialized_at和新授权模式 → 同事务写审计 → commit。事务中任一步失败不得留下半初始化状态。

页面只提交口令、确认和幂等键，不接收可冒充目标的issuer/subject。传入其他身份字段应拒绝。口令不进URL、日志、页面预填或分析脚本；`no-store`；支持密码框但不回显。同一时刻多个账号只能一人成功；完成后删除部署秘密仍保留超管。

## 6. 角色管理与管理写入门禁

| 操作 | user | admin | super_admin | 发布机器身份 |
| --- | --- | --- | --- | --- |
| 公开商品/已公开下载 | 按公开规则 | 按公开规则 | 按公开规则 | 按公开规则 |
| 维护商品、软件草稿/文件 | 否 | 是 | 是 | 仅既有草稿/上传接口 |
| 校验并公开/撤回软件版本 | 否 | 是 | 是 | 否 |
| 列出用户、授予/撤销管理员 | 否 | 否 | 是 | 否 |
| 新增/转交超管 | 否 | 否 | 近期重认证后确认 | 否 |
| 首次绑定 | 仅未初始化、正常登录且持有效初始化口令 | 同左 | 已完成不再允许 | 否 |
| 运维紧急恢复 | 否 | 否 | 另走受控运维流程 | 否 |

`getStoreAdmin()` 保留为既有页面的兼容调用名，内部改用角色服务；新增 `requireSuperAdmin()` 只服务角色/审计管理。角色库异常必须与“普通用户”区分：管理操作报可处理的不可用错误，不允许回到legacy名单。JWT不保存长期有效角色作为唯一来源；角色提交后下一次请求查到新版本。只允许请求内去重，不做无失效机制的跨请求缓存。

授予、撤销、禁用和超管转交在一个SQL事务中：重验操作者 → 锁installation和双方账号 → 检查expected_revision → 检查最后有效超管 → 变更role/status、增authz_version → 写审计。普通管理员直接POST也要拒绝。v1优先停用而不是硬删除身份；必须保留历史审计关联。身份服务在商城外删掉账号不能被此计数完全防止，须有恢复路线。

**跨存储风险必须单独解决**：当前商品变更写JSON，角色写SQL，并不是一个全局事务。上传或哈希耗时阶段在临界区之外，最终保存/发布时必须重验权限与版本。ADM-09必须明确临界区/统一写入协调和故障语义，验证“撤销已返回后，旧请求不得再以旧权限提交”。单纯在入口查一次、提交前再查一次但无协调，仍存在竞态，不能宣布满足标准。若双存储方案无法在断连/崩溃情况下证明约束，需在ADR选择事务化管理变更意图/outbox或将必要元数据纳入同库后再放行生产；禁止用免责声明替代该上线门槛。

匿名下载不调用角色库；即使新增库故障，也保持当前发布目录读取和已发布字节服务。业务审计JSONL与角色事务审计是不同对象；不能把已有JSONL文件冒充满足初始化原子审计。

## 7. 页面、动作和错误契约

以下均是拟新增界面；当前是否已实现以任务账本为准。

| 页面/动作 | 行为 | 禁止或失败状态 |
| --- | --- | --- |
| `/setup/admin` | 登录状态、安装状态、确认当前账号、输入一次性口令 | 不显示口令摘要/原文；不允许选择他人为首位超管 |
| bootstrap Server Action | 只绑定本次验证会话，防重复提交 | 401/未登录、403/来源不符、409/已完成、429/限流、503/权限存储不可用 |
| `/admin/users` | 分页搜索本应用用户；角色/状态；授权、撤销、停用 | 仅super_admin；普通管理员不能枚举用户或角色 |
| role Server Actions | target主键、目标角色、expected_revision、确认、幂等键 | 409/版本冲突或最后超管；不信前端操作者字段 |
| `/admin/audit` | 分页筛选时间/操作/目标/结果，默认只读 | 不公开秘密或完整外部账号档案 |
| 现有权限提示/个人中心 | 显示当前角色与正确入口 | 未登录、无权、待初始化、存储异常分别提示 |

Server Action的用户错误返回结构沿用 `AdminActionResult` 的可见错误反馈；HTTP状态表主要约束将来JSON接口和测试，不要求RSC响应机械使用同一状态码。`redirect()` 留在预期错误捕获之外。支持键盘、390px移动宽度、明确确认、提交期间禁用与错误保留输入；不能仅靠UI限制权限。

## 8. 旧白名单迁移与回滚

生产当前是旧名单授权，不能通过部署新代码就悄悄给任何人超管。按以下有序步骤：

1. **预检与备份**：只读盘点旧模式、受信任身份映射、真实管理员数量、持久安装ID、目录与数据库备份；不把秘密/名单全文写进仓库。
2. **显式授权进入迁移窗口**：已有实例记录为legacy；部署负责人准备受控初始化凭据。旧名单只能在明确legacy阶段使用，不作为数据库故障回退。
3. **绑定首位超管并迁入已确认普通管理员**：操作者通过正常登录认领；其余被确认身份仅迁为admin，不一律升级。首位角色、迁移记录、完成标记与切换模式同一授权事务完成。
4. **检查所有入口切换**：商品动作、上传、所有管理页和API均以新角色库为准；然后删除旧环境名单/一次性口令。改变旧名单不会重新授权。
5. **回滚约束**：能够保留新角色库的新版本可回滚UI；禁止直接回滚到重新启用历史名单的镜像。确需旧代码时先停管理写入、对账撤权名单并由运维确认，不能自动恢复已撤销账号。

`authorization_mode` 是持久控制状态，不能通过普通URL或环境变量随意切回legacy。旧模式支持应标明退出版本/移除条件，避免成为永久双权限来源。

## 9. 容器运维、恢复和实际验收

Docker运行非root，授权库/私有安装标识不与 `/releases/**` 公开目录混放。SQL连接角色权限最小化；初始化秘密只运行时读。容器启动检查区分liveness、管理readiness、公开下载状态；一个权限库故障不得导致公开下载被身份中间件阻塞。多副本初始化使用共享事务锁，同时仍声明业务catalog单写者限制。

安装/迁移/恢复命令的名字须在实现后才进入“可执行命令”部分；本计划不提供伪造可用的恢复CLI。拟实现的恢复任务：备份 → 校验installation与目标已验证身份 → 独立运维确认 → 原子更换角色/审计/失效旧会话 → 清理临时授权。不能清空initialized_at或用旧bootstrap Token再次认领。正常密码/MFA问题先走身份方恢复。

敏感超管转交应使用真正的新OIDC认证结果。不能把JWT刷新时间、页面打开时间或前端“已重新登录”标记当成auth_time；须在测试身份服务与真实Casdoor分别核验 `prompt=login`/max_age 与验证后声明。当前会话回调只保留最小身份，新增认证时间必须审查最小化范围。无法证明近期认证时禁止超管转交，不静默略过。

生产验收是独立里程碑：真实负责人账号绑定 → 删除部署初始化秘密并重启 → 角色保留 → 正常用户登记 → 授予admin → 登录并实际保存测试商品草稿 → 撤销 → 旧会话下一管理请求失败 → 审计可追踪 → 匿名下载仍正常。使用专门测试草稿，不更改真实软件current。

## 11. 测试、证据和发布口径

详细用例见 [TEST_MATRIX.md](TEST_MATRIX.md)。现有测试是回归基线，不等于新增权限用例已经覆盖。每个ADM任务完成需要代码路径和对应验证证据，生产任务另外需要实际部署/账号验收；没有测试数据库、无法读部署或真实身份未准备时写明阻塞，不能通过关闭门禁制造绿灯。

证据分四层：提交SHA及变更范围；本地单元/集成/浏览器输出；CI任务结论；生产health和业务请求结果。已观察GitHub部署步骤缺凭据而网站仍更新，必须按不同通道记录，不归因于失败的部署job。health版本只证明一个版本响应，不证明超管已绑定、商品已上架或包可下载。

进度更新是每个有意义检查点的事务：先附证据 → 更改TASKS任务和revision → 刷新PROGRESS → 更新CURRENT_STATE/HANDOFF → 追加SESSION_LOG → 执行 `npm run handoff:check` → 提交。更换执行者时释放认领，不依赖聊天或AgentDock任务ID才能理解当前状态。

## 12. 依据与待确认项

确定约束来自项目内CT-ADMIN-001；原有产品/隐私边界见 [DECISIONS.md](DECISIONS.md)。以下一手文档用于实现审查，不替代实际工程验证：

- [OIDC稳定身份](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability)：主体键的范围。
- [OWASP授权原则](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)：默认拒绝、逐请求授权。
- [PostgreSQL显式锁](https://www.postgresql.org/docs/17/explicit-locking.html)：事务与互斥设计参考，不声明生产已部署某版本PG。
- [NextAuth v4 callbacks](https://next-auth.js.org/configuration/callbacks)：对照本项目锁定版本验证会话回调。

待确认但不阻止编写本计划：授权数据库的实际部署落点/网络；实际部署触发通道；真实超管账号的MFA与重认证能力；旧管理员清单迁移范围。以上分别由ADM-01、OPS-01、ADM-13与ADM-10处理，不向用户索取明文密码或登录Cookie。
